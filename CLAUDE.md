# garmin-datastore — notes for Claude sessions

Syncs **all** Garmin Connect data into Supabase from a Vercel worker, and exposes it to Claude
through an OAuth MCP connector. Read `docs/requirements.md` (what/why) and `docs/design.md`
(how, plus per-milestone results in §15–§19) before changing anything.


- **Deploy:** run `& 'C:\Users\korte\AppData\Roaming\npm\vercel.cmd' deploy --prod --yes` **in the user's
  terminal tab** (`run_in_terminal`). The Vercel login lives there, not in the agent's sandboxed shell.
  Use `vercel.cmd`: PowerShell blocks `vercel.ps1`. No Git integration yet; deploys are CLI only.
- **Migrations:** write the SQL to `supabase/migrations/<timestamp>_<name>.sql` **and** apply it with the
  Supabase MCP `apply_migration` (same SQL). Use `execute_sql` for reads/one-off checks. Run `get_advisors`
  after DDL. RLS is on everywhere; reader tables need a `gds_reader_select` policy plus a grant.
- PowerShell 5.1 reads files as ANSI: don't rewrite UTF-8 files with `Get-Content`/`Set-Content` (it garbled
  `§` once). Use the Edit tool. `vercel link` re-appends `.vercel` / `.env*` to `.gitignore`; that's harmless.

## Secrets — rules

- All secrets live in **`.env`** (git-ignored) → `gds setup` pushes them to Vercel (and the tick/alert ones to
  Supabase Vault). **Never read `.env` contents, print secrets, or ask the user to paste them in chat.**
  Append non-secret lines with `Add-Content`; secrets go in through hidden prompts the user types in their
  own terminal (`gds auth`, `gds owner-password`) or are generated by `gds setup`.
- `gds auth` = one-time Garmin login (no MFA) → encrypted token row `garmin.garmin_tokens`. Garmin often 429s
  the first login strategies; the library falls back. **The cloud never does password logins.**
- Resend key is a **sending-only key restricted to mail.lilic.dev**. Resend's API (behind Cloudflare) rejects
  urllib's default User-Agent (error 1010), so always send one.

## Architecture in one screen

- `gds/engine.py`: `run_tick`: lease (`garmin.leases`) → `plan` → process `work_units` by priority within a
  240 s budget → `sync_runs` row. Units are `(domain, scope_key)`; outcomes `done/empty/failed`;
  backoff 5 min→6 h, `failed` after 6 attempts. **Unknown domains are skipped, not failed** (a tick on an
  older deployment can see units created by a newer one). The planner only re-creates units when
  `accounts.planned_signature` (day | backfill start | registry) changes.
- `gds/domains/`: **registry of 179 domains** (`daily`, `range` = YYYY-MM, `snapshot` = "latest", `entity`,
  `index`, `activity`). Each is `fetch(src, key)` + optional `normalize(raw, key) -> Rows`. Rows may include
  `work_units` (create child units) and `_replace` (delete rows absent from a full snapshot). Raw JSON is
  always stored gzipped in `raw_objects`; FIT zips in `activity_files`. A changed payload hash re-normalises.
  Adding a mapping later = write the normaliser + `gds renormalize <domain>`.
- `gds/source.py` maps library errors → `RateLimited` (account cooldown 15 min), `Blocked` (403, 1 h + alert),
  `AuthFailed` (needs_reauth + email), `Transient` (unit retry).
- `gds/broker.py`: **Garmin rotates refresh tokens**, so refresh only under a `FOR UPDATE` row lock with
  <20 min left. Never create a second Garmin client from a stored token outside the broker.
- `gds/tools.py` + `gds/app.py`: MCP tools (read-only, as `gds_reader`, 5 s, 500 rows). `gds/oauth.py`:
  Postgres-backed OAuth provider for the MCP SDK 2.x (`MCPServer`, not 1.x `FastMCP`).
- Time: daily rows keyed by Garmin's local `calendarDate`; per-day `utc_offset_min` from the payload (travel-safe).

## Garmin data quirks (already handled; don't "fix" them back)

Weights in **grams**; weather in **°F/mph** (`temp_c` is generated); calendar activities in **ms + cm**, naps in
seconds and **without ids** (`nap:<start>`); FIT running cadence is per leg (×2 → steps/min); lactate
threshold speed is in an undocumented unit (stored as `_raw`); five `get_daily_*_stats` endpoints reject a
month (fetched in 7-day chunks); the scheduled-workouts calendar takes 1-based months (the library converts).

## Starting M5 (writes to Garmin)

Spec: requirements §4.6 (W-1..W-8, FR-17..19), design §8.3. Plan:
1. Migration: `garmin.write_log` (tool, input, preview, garmin_response, status, created entity kind/id,
   `created_by_system`, idempotency key unique).
2. `gds/writes.py` + write tools in `gds/app.py` with `ToolAnnotations(readOnlyHint=False, destructiveHint=…)`.
   Library methods (garminconnect 0.3.19): `add_weigh_in_with_timestamps` / `add_body_composition` (W-1);
   `upload_running_workout`, `upload_strength_workout`, `upload_workout` (W-2); `schedule_workout`,
   `reschedule_workout`, `unschedule_workout` (W-3); `add_hydration_data`, `set_blood_pressure`,
   `set_activity_name/description/type`, `add_gear_to_activity`, `create_manual_activity`,
   `create_gear` / `set_gear_status` / `set_gear_default` (W-4..W-8). Get the client via `broker.open_client`
   and wrap calls in `Source` so errors map the same way.
3. Workout builder: a simple documented JSON spec → Garmin workout JSON; validate against existing
   `workout_detail` entities (real examples are already in the DB).
4. After each write: `engine.request_resync` for the affected domain/date (weigh-ins → `body_composition`
   month; workouts → `workouts` snapshot + `calendar_month`; activity edits → that activity's units).
5. Ownership: reschedule/unschedule/delete only entities whose `write_log` row has `created_by_system`.
6. Test against the real account with clearly labelled test items, then remove them. **Blood pressure's
   normaliser is unverified**: confirm the payload shape after the first BP write.
